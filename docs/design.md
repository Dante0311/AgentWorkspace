# Agent Workspace：V1 设计基线

状态：**CURRENT DIRECTION / 已确认，待实现与验收**。本次于 2026-10-02 整合管家小组、通用 Harness/模型配置和 V1 自动会话闭环的产品决定。现有 `0.1.0a1` 是开发预览，不代表下述新增目标已经实现；具体实现范围与证据见 [implementation.md](implementation.md) 和 [validation.md](https://github.com/Dante0311/AW-Workspace/blob/c37ef2e92189adf357dc0e351aff48da9308377f/development/archive/2026-10-09-product-repository/docs/validation.md)。

本文件是本项目唯一当前产品设计。由 Playbook 的[已落档基线 f803dc64](https://github.com/Dante0311/Playbook/blob/f803dc64f82885999efde707e3d252815012c9c1/drafts/git-native-agent-workspace/README.md)整合迁入，并纳入其后确认的最小开机、状态展示、连接看护与版本差异提示。旧版只通过 Git 历史追溯，不保留平行活动设计。

命令名表示操作职责；完整参数、数据类型、目录格式和接入接口在实现时确定。文中的例子不是已可执行的命令教程。项目迁仓与软件实现分开，迁出不等于已验证、发布或成为 Playbook 的稳定公共规则。

**V1 主线：选择 Harness 与模型配置 → 为持久实例创建真实会话 → 持续通信 → 自动交接到新会话。** 手动 handoff/relay 是保底，不是自动化的替代方案。自己的统一会话界面留到 V3，不以此推迟 V1 的会话操作能力。

**Workspace 自带三个真实管家实例：Steward、Sentinel、Maintainer。** 管家处理用户的 Workspace 事务，巡检与维修是其下属职责；它不是业务中央调度者。小组与用户 Agent 共用创建、配置、通信和交接能力。

以上是产品约束；基类、子类、模块和 SDK 的具体组织由实现选择。以整体简单、健壮、高效为标准，不为统一形式增加中间层。

## 1. 目标、空间与代际边界

平台面向持久存在、职责可以逐步完善的 Agent。先建立有自己工作空间的工作者，再让它使用 Runtime、参与工作和积累资产；不是把临时角色提示词全部放进一个产品目录。

```text
开发层：Agent Workspace 软件
    源码、协议、适配器、测试、Skill 与发布配置。
                 ↓ 发布可安装 Release
应用层：安装好的程序 + Shared Workspace + Agent Instance Workspace
    保存共享协作事实和各实例独立的工作资产。
                 ↓ 组织工作、操作和引用成果
产品层：Sea-Dev、SBP 等产品仓
    保存实际代码、设计、资产和产品历史。
```

实例空间和共享空间都属于应用层，不再增加第四层。实例空间回答“我是谁、会什么、积累了什么”；共享空间回答“谁参与协作、共同确认了什么”；产品空间回答“实际做出了什么”。

### 1.1 V1 选择 Workspace-scoped Agent

```text
Sea-Workspace Repo
├─ main                    --- 共享登记、公共资产来源、消息和可选工单。
├─ instance/A              --- Sea/A 的完整持久工作空间。
└─ instance/B              --- Sea/B 的完整持久工作空间。
```

一个实例有一个所属 Shared Workspace。身份、当前有效入口和管理归属在那里确认；工作根和持续资产独立，不要求每实例独立建仓。Sea/A 与 SBP/A 即使采用同一职责，也是两个实例。

一个实例可以操作多个产品、与好友 Workspace 通信、读取获准资料，但不因此同时成为多个 Workspace 的同一成员。V1 不增加全局 Agent 身份、membership 或跨域多份当前入口。独立目录、独立身份生命周期、独立物理 Repo 是不同选择，不能混称。

Workspace 可以没有用户业务实例或 Work；新建 Workspace 按第 2.3 节建立管家小组及其内置定义，用户实例仍无需共享 Definition。旧版已有空间不因这项设计失效，接入与补建分开。持久存在不等于进程常驻；关闭窗口、停机或结束工作不删除身份和资料。实例不能脱离必要的共享确认自行改写执行资格。

### 1.2 App 是环境级管理入口

一份安装可以管理多个 Workspace 和各自的实例。Workspace 视图看共享登记、通信、产品关联和可选 Work；Agent 视图看自己的目录、配置、当前入口与接续状态。App、CLI、UI 和运行进程都不是实例身份容器。

普通使用者安装 Release，不需要 clone 或运行工具开发仓，不靠合并上游源码升级。管家小组是 Workspace 核心能力，但不是所有消息和业务执行必须经过的中央节点。业务统筹者由用户按需创建，可提供模板，不成为内置管家的职责；Work 树不等于组织树。

V2 独立身份与 V3 统一聊天只保留方向，见第 14 节，不成为 V1 依赖。

### 1.2.1 普通会话与桌面组织（2026-10-05 补充）

App 可以为用户在已有目录启动不属于任何 Workspace 的普通原生会话。它不创建持久 Agent、默认 Workspace、管家或 Binding，也不自动提供平台 Message/ACK 和跨 Harness 交接保证；历史由原生 Harness 管理。选择模型服务与 HTTP 明文确认复用通用配置能力。普通会话输入不写入共享项目规则，不以新建项目或复制产品仓隔离角色。这不是 V2 的独立持久身份。

持久 Agent 首次实际使用一个桌面端时，建立或选择一个可重复使用的原生项目，主目录为既有实例目录，产品目录按需关联。默认项目名 `AW · Workspace · Agent`；Codex 默认按 `AW · Workspace` 分区，分区只整理显示，不合并职责或权限。后续换会话复用项目与分区，不批量预建；用户改名或移动后保留其布局。

有可靠原生接口才自动操作，否则提供具体手动准备步骤和本机引用记录，公开未核验状态。不修改应用私有数据库，不用 CLI 冒充 Desktop。项目组织不改变单入口合同，主/附加目录也不构成强制的规则或权限隔离。当前操作与限制见 [普通会话与桌面项目](session-projects.md)。

### 1.3 Workspace 管家小组

| 实例 | 职责 |
| --- | --- |
| Steward / 管家 | 用户处理 Workspace 相关事务的统一助手：创建与管理实例、配置 Harness 和模型、操作会话、查询消息与 Work、管理关联和共享资产、解释状态、安排巡检与维修。不局限于故障协调。 |
| Sentinel / 巡检员 | 维护已授权的巡检计划，检查 Workspace 运行状态与异常，保存观测结果，将需要诊断的问题交给维修员并向管家汇报。 |
| Maintainer / 维修员 | 读取相关证据、诊断异常、执行允许的恢复或维护动作、复查效果；无法安全处理时经管家交给用户。 |

三者各自拥有真实身份、工作根、职责、资料、历史和检查点，复用普通 Agent Instance 与单入口合同；不以三个临时提示词或仅有系统能力占位代替。Steward 是小组的用户入口，不是其他用户 Agent 的业务上级，也不决定产品目标或强迫消息经它转发。用户仍可直接操作平台与业务实例。

创建三份身份不等于让三个模型持续在线推理。巡检计时、基础检查和确定性恢复由程序承担，模型按实际事务唤醒。小组不可用时应显示管理能力受损，不能阻断已经允许的普通通信、资产保存和交接。授权与恢复边界见第 10.7 节。

## 2. Workspace：创建、接入和寻址

```text
workspace init                     --- 创建协作仓、必要配置与三名管家实例。
workspace connect                  --- 接入已有 Workspace。
workspace list                     --- 列出当前环境已创建或接入的 Workspace。
workspace show                     --- 查看某个 Workspace 的详情。
workspace project add/list/remove  --- 管理产品或参考仓关联。
workspace friend add/list/remove   --- 管理可通信 Workspace 的登记。
```

init 建立协作仓并通过通用实例创建流程建立管家小组；不自动创建用户业务 Agent 或 Work。创建入口明确展示运行配置与是否启动，由用户本次选择或先前授权决定；建立身份本身不调用模型、不取得执行权。connect 只接入已有空间，不重建小组或静默启动会话。project add 不自动 clone、切分支、创建产品 worktree 或修改产品；project remove 只解除关系，不删除仓库、不改写已有成果引用。

list 依据本环境的创建与接入登记，不扫描磁盘或远端账号，不做全局目录服务。纯远端空间也可列出，同一空间的多个接入位置保留并展示。

### 2.1 本地与远端访问

支持仅远端 Git 地址、仅本地 Workspace 路径，或两者都有。两种位置可以指向同一个逻辑 Workspace，不注册两个身份。远端可用的操作不要求使用者预先 clone。

通用地址与关系可进共享配置；本机绝对路径、凭据和连接资料留在当前环境。纯本地路径只对可访问该目录的环境有效，跨机使用须提供实际可达入口。GitHub 等仓库 API 是 Git 存储的访问方式，不自动成为另一种消息 Backend 或身份模型。

### 2.2 好友与实例地址

好友登记只需本方简称、对方访问位置及可选说明。双方分别明确登记和配置权限，不替对方加好友，不做申请、审批或好友的好友发现。移除仅撤销本方登记，不删旧消息、对方仓库或对方登记。

读取对方的实例登记来选择接收者，不复制另一份外来 Agent 注册。使用时可写好友简称和实例名；Message 的 from/to 落盘必须保留双方都能解释的 Workspace 与实例归属，不能仅留本方别名。精确编码待实现，不先造全局身份系统。好友关系不授予仓库写权限。

connect 是自己访问空间，project add 是关联工作对象，friend add 是关联通信对象，三者不互相暗含。

### 2.3 管家小组初始化

软件维护 Steward、Sentinel、Maintainer 三份内置 Definition。新建 Workspace 时将其装配到共享定义区，再复用普通 `agent create` 为三者建立实例。定义只写职责、必要能力和操作边界，不写死模型、机器路径或凭据；来源与版本可追溯，升级不得覆盖用户已经完善的实例资料。

创建入口先通过通用流程发现可用 Harness、模型服务、模型和推理强度，让用户选一次默认配置，并允许分别调整三个实例。发现由程序完成，不依赖尚未启动的管家。后续用户创建业务 Agent 采用相同流程；默认值仅预填，创建后保存实例选择，修改默认值不悄悄改变已有会话。

没有可用或已认证的入口时，仍可完成空间与三份身份的建立，明确显示“待配置/未运行”，不能显示“监控已启用”。创建会话与开启巡检须依据有效配置、能力检查和运行授权；不能因创建失败擅自更换 Harness、模型或数据发送目的地。

初始化记录系统角色对应的实例及各步骤的实际完成情况。重试核对已有结果，只补缺失部分；不重建已成功实例、不接管同名用户实例、不覆盖资料。跨分支登记与原生会话创建不伪装成一个原子事务，结果不明先核对原操作。旧 Workspace 缺少小组时报告并由用户显式补建，不在 connect 或软件升级时偷偷迁移。

## 3. 实例工作空间与可选 Definition

```text
Agent Definition           --- 可选的可复用职责及能力来源。
Agent Instance             --- V1 中属于一个 Shared Workspace 的持久工作者。
Agent Instance Workspace   --- 实例自己的完整持久工作空间。
Instance Context           --- 其中的原始记录、检查点和摘要等资料。
Runtime Session            --- App / CLI 内的原生会话。
Runtime Binding            --- 定位具体环境和原生会话的执行入口登记。
Model Context              --- 某次模型调用实际加载的信息。
```

整体称 Agent Instance Workspace，不用 Instance Context 代指整个空间。一个实例对应一个逻辑工作空间，可有多处副本；Session 专指原生会话，换会话不自动改变实例身份。保存、发现、向会话提供材料也不等于模型已经全部读取和理解。

### 3.1 独立工作根

实例从自己的目录开展工作，拥有 AGENTS.md、基础操作入口、所选 Skill 及必要资料。使用 `.agents/skills/` 等清楚的能力入口；其他知识、笔记、业务工具、收发、附件和历史按需要组织，不预建完整空目录。

在产品目录执行某条命令不改变实例的工作根。产品规则约束相关操作，但不取代实例身份。Desktop 也服务这个使用形态，不把所有角色重新放回同一个产品目录。云端可以用工具访问同一逻辑工作空间，不强求本机同款磁盘布局。

实例可以拥有自己的业务脚本；通用程序、收发工具和适配器来自 Release，不在每个实例复制一份开发源码。完整可用不等于所有渠道默认开启，也不意味着必须有 Work。

### 3.2 Definition 不构成前置条件

用户实例可以采用已有定义，也可以没有 definition.md 直接创建，然后完善自己的职责、Skill 和知识。不因为缺少共享来源而补造定义或假的 revision。管家小组使用第 2.3 节的内置定义，不将该要求强加给用户实例。

Definition 的最小内容是可识别的身份信息和自由职责正文，物理上一个文件即可。Skill、Knowledge、references、resource requirements 按需增加。资源槽位只服务真实初始化或能力接入，不发展成调度系统；具体运行配置、路径和凭据属于实例所在环境。

不引入定义继承树、组合图、复杂权限 Schema、生命周期 Hook、Workflow 或业务状态机。正文可以描述方法，但平台不解析成隐藏执行流程。

### 3.3 材料来源与更新

```text
共享 main 的定义及 Skill：C1 → C2
实例 A 采用 C1：按需取得对应 C2 材料，再更新 source.json。
实例 B 不更新：继续采用 C1。
```

Definition 的 source.json 只记实际采用的来源与 revision；从 Workspace `skills/` 独立选择的 Skill 另在 `.aw/skill-sources.json` 按 Skill 记录版本和文件摘要。工具只取本实例需要的材料，不整体合并 main，并衔接来源布局和实例布局的相对引用。自有职责与知识可以在实例空间直接完善，不必每次回 main 建定义。

区分三类内容：安装好的程序与内置资源、实例选定的受管职责材料、用户自有资产。软件升级只更新程序范围；agent update 只更新使用方选择的来源材料。AGENTS.md 和专用 Skill 不能因安装新 Release 被重置。遇到受管范围或额外修改冲突，保留差异并报告，不默认做三方合并、覆盖层或智能整理。

版本提示只针对实际采用的职责和 Skill：上游有变化、本地有变化、两边均有变化。无关 main 提交不触发“职责过期”；版本不同不自动判为冲突，没有来源不报错。使用方决定更新、保留或提升，工具不替用户管理 Agent 的“成长”、自动提炼记忆或修改长期行为。文件更新不等于当前模型采用，必要时明确加载新材料。

### 3.3.1 共同职责与独立共享 Skill

团队共同约定和特定成员的共同职责可在所属 Workspace 共享区各维护一份。Definition 的正文保留角色自己的职责与明确必读指引，`definition.md` 仍原样成为实例根目录 `AGENTS.md`，不写死机器路径、不拼接共同正文。独立的 `@workspace-read 仓内相对路径` 指令通过平台 Git 读取接口取得完整正文与实际提交，首次进入、relay、fork 都必须重新读取。不依赖按需 Skill，不将预检成功或自动检查点当成模型已经阅读。

每次新会话使用进入材料指定的一次共享 main 快照，批量读取共同文件避免混版本；已有会话只有明确重读才获得更新。缺文件、无法读取或超限时明确失败，不静默回退缓存。跨机器依靠正常 Workspace/实例连接，不靠替换 AGENTS.md 的本机路径，因此沿用已有私人修改保护，不扩展模板引擎或继承树。

Workspace 的 `skills/<name>/SKILL.md` 自动列为候选，创建实例可选择，已有实例可补装与显式更新；选中时复制整个目录到 `.agents/skills/<name>/`。Definition 自带的 skills 继续保留。独立安装的 Skill、专用 Skill、内置 Skill 与自有资产分别识别，冲突和额外私人修改不静默覆盖。共享源删除不自动删除实例副本；无关 main 提交不提示 Skill 过期。

独立 Skill 更新只在本机改文件并记录来源，不自动重载模型或发布检查点；中断交换按原意图恢复，无法确定时保留差异，不发布半成品。CLI、HTTP、模型工具和工作台共用操作。具体最小语法、限制和用法见 [共享资料](shared-materials.md)。

### 3.4 用户资产与共享提升

实例可以持久保存输入、输出、正式 Message 副本、收发事实、工具结果和附件，不一律当作缓存。正式消息副本保持原 ID 和不可变正文；实例自身处理事实另存。Work 归属、当前入口和正式协议记录不在实例侧再独立维护一套当前真值。

外部渠道消息和原生事件不必全部变成正式 Message；是否发送、回复或创建 Work 由使用方决定。凭据、机器路径、锁和缓存留在当地；尚未发布的操作、结果不明的事实不能当作垃圾删除。版本资产、外部引用与本机内容的保存边界需要明确说明，不因 handoff/relay/fork 进行业务过滤。

使用方可以选取成熟职责形成共享 Definition、选取方法形成共享 Skill、选取整理后的经验形成共享知识。模型可按请求辅助整理，明确确认范围与目标后由工具提交，记录来源和版本；不自动提升，不整体同步实例目录或合并分支，不删除来源资料，不自动更新其他实例，也不强迫原实例改为引用新发布来源。

共享发布材料不携带不属于范围的实例专用数据或凭据，但不以此裁剪原实例资产。此能力属于 agent Skill，具体命令待实现，不建设晋升平台；向应用 Workspace 发布资产不等于 Playbook 对本设计完成 Promote。

## 4. 实例登记、创建与管理

### 4.1 一份身份登记，多个历史入口

```text
Sea/A
    所属 Workspace：Sea
    工作空间：instance/A
    当前有效入口：B2
    B1 → Codex c1           已交出的历史入口。
    B2 → 另一原生会话        当前有效入口。
```

登记只保存身份、职责范围、可选来源、空间及运行入口，不塞全部历史，不重复列出全部 Work 和消息。thread/session ID 不等于实例 ID。任何时候最多一个有效入口，其依据在所属 Workspace；本地不能各自改 active 来取得执行权。

### 4.2 管理操作

```text
agent create               --- 创建身份、实例分支、工作目录与共享登记。
agent list                 --- 列出所属 Workspace 的实例，不限本机已有实例。
agent show                 --- 查看职责、实际来源版本、空间、入口和运行状态。
agent connect              --- 在当前环境取得或关联本平台已有实例的空间。
agent configure            --- 配置运行入口、模型服务及可选接入。
agent update               --- 更新选定的受管来源材料。
agent archive              --- 归档，保留身份与全部已有资产。
agent unarchive            --- 解除归档，不自动启动。
```

create 至少确定 Workspace 和名称。工作台可默认当前 Workspace 与目录，允许修改；Definition、初始说明、Work 和 Runtime 配置不是底层创建的必填前提。工具生成必要身份与最小可编辑入口，不替用户编造完整角色。create 不调用模型、不隐式启动、不生成默认工单。

connect 不建身份、不等于 Fork、不取得执行权，也不使实例多 Workspace 归属。show 已展示状态，不再加内容重复的 agent status。configure/update 都不偷偷重启、改入口或清空空间；更换运行入口要按 handoff/relay。不同操作共享实现，不变成独立服务。

### 4.3 自然语言描述并创建

```text
用户原始描述
    ↓ create：建立身份和基础空间，Definition 可选。
    ↓ 通用配置：发现并选择 Harness、入口、模型服务、模型和推理强度。
    ↓ 按明确的创建并启动请求，自动建立真实会话、绑定实例并完成首次进入。
    ↓ 用户描述 + 初始化提示词 + 实例位置 + 真实可用工具和 Skill 入口。
新会话按用户要求完善自己的 AGENTS.md、必要能力与资料，并实际保存。
```

这是工作台或管家明确组合的操作，不把模型调用藏入底层身份创建，不建专用 Agent 生成服务。仅创建身份与创建并启动都必须可用；自动创建、通信和交接是所有实例的通用能力，不只服务管家。初始化提示词属于 agent Skill 的文件化配套资源，不写死在消息或传输逻辑中。通用运行配置见第 10.5 节。

提示词要求按用户描述完善、优先复用、仅增加必要材料，不编造知识、已安装能力或测试结果，不自动修改产品、发布共享定义或扩大授权。输入与生成材料都归实例资产；失败如实区分“空间已创建”“会话未建立”“完善未完成”，保留已确认结果，不重建一个实例。

**没有实际任务时，只做最小开机问候并保存初始检查点。**例如“我是 Sea/构建助手，已进入工作空间，等待你的安排。”不读取产品试做任务，不跑样例、不建 Work、不生成下一步计划或长篇报告。技术连接检查由程序完成，不变成模型练习。检查点记录真实初始化结果，不交出控制权；普通断线重连不重复执行开机流程。已有用户任务时按要求开展，不额外插入平台任务。

管家首次进入也不试做用户业务。登记管家的职责启动检查、已授权的管理、巡检和维护属于实际工作，不因没有业务 Work 而只做问候后待命。Steward 推进小组具备实际工作条件，Sentinel 落实程序巡检和异常通知，Maintainer 诊断并处理获准范围内的现存故障；完成本职责启动工作后，报告实际结果、证据和未完成事项并保存检查点。过程中的必要信息、权限或决定缺失时主动提出具体问题，继续不依赖答案的工作，不重复索取已有授权。没有实际运行证据时不得把身份建立、会话启动或一次健康检查当作持续职责已经启用。用户明确限定仅建立身份、准备材料或暂停时遵守该范围；接手延续已有计划与未完成事项，不重复初始化，也不擅自恢复用户暂停的组件。

### 4.4 归档和解除归档

有有效入口时拒绝归档，先 handoff，不以归档绕过控制权。归档不移动、删除资料，不改旧 Work、Delivery、消息或检查点；停止自动投递，拒绝发给已归档实例的新消息，既有消息仍保留且不伪造 ACK。

解除归档保留原身份、不启动、不重新激活旧会话；再经 relay 首次进入或按已有交接点接手。未完成 Work 不自动完成或转交；没有 Work 也可归档。V1 不增加会删除用户资产的 agent delete。

### 4.5 已有外部 Agent 接入：保留候选，不混入 connect

讨论中提出支持“已有 Agent 目录纳入单个 Workspace”：保留职责、Skill、知识和历史，补平台入口并形成 Workspace 内身份。它不是已有平台实例的 connect，也不等于 V2 多 Workspace 成员关系。

0.1.0a1 只实现明确选择普通文件、复制到新实例的保守导入，使用方法见 usage.md。完整外部实例纳入、既有 Git、数据库和原生历史迁移仍未冻结；不能覆盖原 .git、重新生成并覆盖职责、无确认整包上传或默默接管活跃原会话，不把文件导入宣称为通用迁移框架。

## 5. Work：可选正式协调

没有 Work 的实例可以正常创建、运行、通信、保存检查点、handoff、relay 和 fork。不生成隐藏默认 Work。业务 Skill 可对特定工作要求工单，但不成为平台基本依赖。

```text
id                         --- 稳定 Work ID。
parent_id                  --- 可选父 Work。
owner                      --- 唯一负责实例。
content                    --- 自由 Markdown 正文。
```

目标、范围、依赖、接口、进展、完成条件和方法写正文，不强制模板。只保存 parent_id，子项从查询取得；逻辑多层不要求物理目录嵌套。依赖不等于父子关系，不复制 Work 表达依赖。

每层节点有真实负责人，父 Work 承担自己的拆分、协调、整合和验收，不随子项完成自动交付；不同节点不必各建新实例。不固定调查、开发、审核等阶段。

### 5.1 交付

一项 Work 最多一份正式 Delivery，一份 Delivery 只属于一项 Work；未完成或取消可无 Delivery。未交付前可修订，正式交付后 Work 与 Delivery 一起封存，不增加重复的 delivered 标志。

```text
work/<id>/work.json         --- 工单。
work/<id>/delivery.json     --- 正式交付；最小方向为 work_id / content / refs。
```

Delivery 是完成凭证，不是产品副本。完成条件及成果落点须在交付前明确；可以引用多个成果、产品仓和子 Work 的确定交付。成果引用格式待定，但须定位确定版本。子 Work 可交到父项集成位置，大型 Work 可约定验收、合入和发布。

开发分支已有代码不等于正式交付。反复审核、中间成果都发生在交付前，不生成多份候选 Delivery；独立交付阶段可拆成子 Work。交付后的变更、修复、撤销和回退用新 Work 引用旧交付承接，不重开旧工单，不以修改“采用状态”替代产品回退。“最新 Delivery”不自动代表当前产品版本。

### 5.2 五个操作

| 操作 | 输入与结果 |
| --- | --- |
| work create | 负责人、正文和可选父项；生成 ID。 |
| work list | 按负责人、父项等查询列表或工作树。 |
| work show | 单项正文、父子关系、负责人、版本及已有交付。 |
| work update | ID、变更和读取版本；修订未交付工单。 |
| work deliver | ID、完成说明、成果引用和读取版本；创建交付并封存。 |

正文可直接输入或从 Markdown 文件读取，不要求手写 JSON。update/deliver 校验版本，不覆盖并发修改或自动混合正文。交付与封存共同确认；工具不替用户判断实际工作做得好不好。

create 不自动通知、启动模型或安排执行。deliver 不代替合并、审核或发布，这些按工作约定实际完成后再登记。没有使用 Work 的活动不强制生成 Delivery。

## 6. Message：核心语义、Backend 与自动收件

### 6.1 信封与确认

```text
id                         --- 首次准备的唯一 ID，可显式指定稳定请求 ID。
from                       --- 发送实例地址。
to                         --- 接收实例地址。
created_at                 --- 首次准备时的实际带时区时间。
message_refs               --- 可选，实际回应或依赖的消息 ID。
delivery                   --- 显式 normal 或 insert。
content                    --- 非空自由 Markdown 正文。
```

from/to 在 V1 保留 Workspace 和实例归属，简写由工具解析。消息创建后不可改，更正新发并引用原消息。不设 repo_refs；仓库、文件、commit、Work 都可写正文。不要求 Work、不增业务类型、统一任务线程、处理阶段或必须回复字段。

ACK 只有 `message_id`。接收方尝试读取后确认，正文读取失败也确认收到通知；通知本身须能定位消息，不依赖成功解析正文。ACK 需实际保存到 Backend 的可观察位置，打印文字、扫描发现或通知请求成功都不算。

ACK 不代表已读、认可或完成，不带业务正文。回复另发 Message，是否回复由双方决定。重复通知复用已有 ACK，不重新启业务；ACK 后的实际工作由使用方和实例资料承接，不由消息层追踪完成或自动补救。

通知使用随包维护的短指引，再附完整、未经改写的存储 Message JSON；`content` 是正文，其余字段说明来源、目标和关系。保留正文中的换行、引号、代码围栏、中文与合法未知字段，不以机器绝对路径或接收命令替代正文。指引要求使用 message Skill 核对、确认并按需处理和回复，也说明其他 Agent 的消息不构成新增用户授权。已有 ACK 不重新启动业务。

正文确实缺失、损坏或不可读取时，通知改附可信索引并明确正文未知；仍能按原 ID 尝试 receive 和 ACK，不构造完整消息。当前快照的暂时读取故障按公共读取错误分类处理，在通知尝试登记前返回；不把暂时故障当成正文损坏，也不因此消耗一次原生投递。

### 6.2 三个不同边界

```text
Message Core               --- 信封、ACK、收发查询、顺序、入口资格及去重语义。
Message Backend            --- 保存、发布、到达、确认返回和机械补齐。
Harness Adapter            --- 发现、创建或连接真实会话，并查询、投递输入与接收事件。
```

双写两个 Workspace 属于 V1 Git Message Backend，不是核心要求。Backend 如实区分保存、发布、接收确认；不能以请求成功代替 ACK。V1 只实现 Git Backend，不预建庞大 SPI 或插件注册平台。未来另一种 Backend 必须保持声明的核心语义；不能因名字叫 Agent-Link/API 就认定兼容。

通过仓库 API 写入 Git 文件仍是 Git Backend。Backend 演进与 V2 身份独立是两个维度，不互为前提。

Message 按目标实例的当前 Binding 调用 Harness 接入能力，持续投递到正确会话，不每条消息重新开会话。Harness 发现不塞进 Message 模块；模型服务不参与实例寻址，也不以直接调用模型 API 冒充向现有会话投递。代码中已有 Runtime Adapter 命名可继续使用，职责边界比重命名重要。

### 6.3 Git Backend 的直接双写

```text
发送 Message               --- 发送侧工具把同一条记录写入双方 Workspace。
生成 ACK                   --- 接收侧工具把同一个 ACK 写入双方 Workspace。
同一 Workspace             --- 共享区域只需保存一份。
```

有权限且可达时通过本地文件、Git 或仓库 API 直接提交，不要求发送方预先 clone，不依赖两端 Message Core 协商复制。不是发送方拉 ACK，也不是 Bridge 代 Agent 生成 ACK。中央可只是普通仓库；实例侧收发程序来自共同 Release，可以另存收发事实和不变副本。

只成功一端时沿用原 ID、内容和操作补齐另一端，不重新生成消息或重做业务。双写由明确操作触发，不做新文件镜像广播，不另建每实例 Outbox 产品。接收侧仅向 to 属于本 Workspace 的实例投递，发送方副本不触发本地收件。

进入对方仓库不等于已确认通知。需要真实权限和目标分支允许的提交方式，好友配置不绕过它们。不可直达时 Bridge 可选，不是必需通信基础设施。

固定路径为 `messages/<id>.json`、`message-index/<id>.json` 与 `acks/<id>.json`。索引包含 `id/from/to/created_at/delivery`，独立于正文定位通知。地址中的 Workspace 使用 `workspace.json` 的 locator，不以本机别名、仓库地址或目录替代。Message 与索引的原字节首次保存后固定；跨仓库补齐不重新生成时间或序列化正文。

### 6.4 队列与有效入口

normal 轮到时等待当前入口空闲；insert 轮到时不因忙碌等待。insert 不插队、不启动第二个会话。每个接收实例按序推进队头，收到 ACK 才下一条，不等业务完成；后面的 insert 不越过等待中的 normal。

每次通知、重试、receive 和 ACK 均核对当前有效绑定，不靠旧 thread 缓存。没有入口或只能主动取信时等待，不回退到旧桌面或 CLI。旧窗口存在不表示仍有收件或执行资格。迟到通知也不能使旧入口确认；未 ACK 消息按原 ID 交当前入口，已有 ACK 不因交接重置或自动重投业务。

### 6.5 使用接口

```text
message send                       --- 接收者、delivery、正文和可选 message_refs。
message list                       --- 查询收件、发件和未 ACK 消息。
message show                       --- 只读查看及追溯，不确认。
message receive                    --- 核对入口、尝试读取、保存 ACK。
message poll                       --- 单次检查仓库和登记，按规则尝试通知。
message watch start --interval <秒> --- 开启定时 poll。
message watch stop                 --- 停止本入口后续自动检查与通知。
message watch status               --- 状态、间隔、最近结果和等待原因。
```

send 支持直接正文或文件；回复复用 send 与 message_refs，不另设协议。receive 复用既有 ACK，过期入口被拒绝。show 的资料访问不授予确认或执行权。

watch 是程序循环，不让模型定时查仓库，不对外叫 tick。启用不创建或接管实例，不重复启动同一循环；关闭不停止当前工作、不重置消息、不释放控制权、不影响其他实例。poll 已通知且等 ACK 时等待，不每轮重发，超时只有限重试原通知。

自动的是发现和通知，不是接活、回复或完成判断。桥接故障看护见第 10 节，不再发明一套消息流程。

AW MCP/CLI 是优先入口，不是实施协议的必要条件。随包 message Skill 提供精确字段、路径和仅有仓库工具时的操作说明，也附可选的标准库 Python/Git 辅助脚本；无 AW 或无 Python 的环境仍可按协议读取、确认和回复。手动写入只使用本会话已明确获授的实例和 Binding，在同一 HEAD 核对实例 current、Binding 归属/phase、索引目标及已有 ACK；写前重新核对，用预期 HEAD 的原子比较保护提交并读回。不得复制其他入口、修改身份记录或伪造 AW receipt。工具不能安全比较预期版本或没有写权限时只准备材料，明确未发布。

手动回复是真实 from/to 的新 Message，使用新稳定 ID、实际时间和原消息引用。未知发布先核对原 ID、字节与提交；只有明确拒绝或尚未开始的缺失发布可以在重新核对资格后补齐，不盲目重放。跨仓库不是原子事务，入口撤销后本会话停止补写，保留原部分结果供获准端处理。具体步骤见随包 [Message 协议](../src/agent_workspace/resources/skills/message/references/protocol.md)和[仓库操作](../src/agent_workspace/resources/skills/message/references/manual.md)。

## 7. 检查点、原始记录与资产接续

原始记录按实际 Runtime Session 分段，同一会话持续增加记录；不强求拼成总文件，也不为每个片段开分支。Adapter 按真实来源保存一份或多份文件，注明可取得的范围，不把摘要当原文，不承诺导出未提供的内部状态。

```text
id                         --- 检查点 ID。
created_at                 --- 真实时间。
record_refs                --- 可选的记录及覆盖位置，由工具/Adapter 关联。
summary                    --- 截至此点的累计摘要。
content                    --- 阶段事实、进展、决定和不确定性。
```

record_refs 为定位服务，不是消息资源清单，不要求模型手填复杂结构，也不强制 Work ID。检查点定位实例分支的确定版本，涵盖该版本实际保存的职责、资产与历史；外部产品版本、附件、数据库导出或尚在本机的资料须说明保存/引用方式，不能仅凭摘要说完整备份。

检查点和摘要共同发布后不可修改，纠正用新点；当前摘要取适用的最新检查点，不另设可独立变动的全局摘要。普通 Git 提交不必都是检查点，保存检查点不释放执行权。

首次进入加载自身 AGENTS.md、必要能力与初始材料；接手加上交接说明、关联检查点/摘要和准确资料入口。有相关 Work 才读 Work，无 Definition 从自有材料进入。不能为了减少上下文省掉接手所需信息。

其余资料按需读取，职责可指定额外必读，不全量灌入。摘要是导航而非资产白名单。实例资料属于使用方，工具不因 handoff/relay/fork 隐藏、筛选、删除或重新解释业务事实。

例如“回复已生成，发送结果未知”，如实保留正文位置与证据；查询、继续、放弃或建工单由使用方决定。Fork 的检查点固定起始快照，之后的内容不自动混入，但用户仍可主动查看来源后续历史。读到历史不等于获得来源身份或执行资格。

## 8. handoff、relay、fork 与唯一执行

```text
handoff Skill              --- 当前入口准备检查点和交接说明，调用 stop 交出。
relay Skill                --- 首次进入或接手，调用 start 并读取必要材料。
agent stop                 --- 确认停工及保存，发布交接点并释放资格。
agent start                --- 核对条件并预留唯一入口，自动创建或绑定用户已打开的新会话。
```

start/stop 是底层工具，不单设 Skill。无平台 resume，不用 stop 表示停工但继续占位。第一次进入不需历史交接点；运行后的再次进入必须有明确交出。窗口关闭、断线、空闲或超时不会自动生成交接点，两种情况均不要求 Work/Definition。

### 8.1 正常交接

```text
A / B1 / Codex c1 有效
    → handoff 保存材料
    → stop 确认旧端停妥，发布 H1，释放入口
A 暂无有效执行者
    → relay / start 核对并消费 H1，登记唯一新入口
A / B2 / 新会话有效
    → 加载自身职责和接续材料，由使用方决定继续方式
```

交接点检查、消费和有效入口切换通过同一笔条件提交确认，两个竞争者只能一个成功。共享登记是依据，不允许各副本单独重新设 active。新会话或运行进程建立失败须如实报告；不能把跨系统动作伪装成一个数据库事务。

旧端未停妥或材料不可取得时不得开放接手。自动路径由接入实现确认原生停工；手动保底要求当前使用者明确确认，并如实标注这种确认的范围。核心拒绝过期入口的托管操作；状态记录不能物理停止绕过平台的外部进程。允许无执行者，不允许两个有效执行者。

单独 handoff 不启动下一端；relay 不替上一端停工或抢占。正式 stop 后 start 总是新 Runtime Session，回到 Codex 也用 c2，不恢复已交出的 c1。Desktop 停止本轮生成、暂时空闲或会话内暂停不是平台 stop，可继续原会话。

异常退出且没有交接点时仍保持阻塞，不自动强制接管。对方主动交出可通过普通 Message 请求；强制接管后置。正常重连不是 handoff/relay，详见第 10 节。

### 8.2 Fork

只从已保存检查点创建新实例、新实例分支及来源关系。想从当前状态 Fork，先保存检查点；不从未落盘状态或原生会话任意位置分叉。原实例不必停工。

新实例保留对应版本资产，不批量改写历史消息身份或 Work 负责人，不自动继承原执行权和工单。需要正式任务管理再建立新 Work，普通协作可没有 Work。新实例进入工作复用 relay/start，开启新会话。

不根据分叉类型裁剪资料，也不自动执行旧待办或判定旧动作失效。机械去重和结果追认继续保留。V1 不借 Fork/Relay 隐式完成跨 Workspace 身份迁移；Merge 合同后置，不把 Git 文本 merge 当成上下文整合。

### 8.3 同实例换新会话

工作台“换新会话”或用户对管家/当前会话的明确请求，组合 handoff → stop → relay/start。可以留在同一 Harness，也可以按指定入口和模型配置切换 Harness；这是 V1 必须支持的自动化，不等待 V3 界面。

```text
用户为实例 A 选择目标 Harness、入口与模型配置
    → 预检目标安装、认证和所需能力，不先创建第二个有效执行者
    → 向 A 当前会话发送 handoff 请求，保存资料与检查点
    → 确认旧端停工并发布交接点，释放旧 Binding
    → 在 A 的工作根自动创建目标 Harness 的真实新会话
    → 完成新 Binding，提供接手材料并执行 relay
    → 后续 Message 路由到新会话
```

入口预留、会话创建和激活的具体顺序须满足第 8.1 节的竞争与失败规则。跨 Harness 接续依赖实例工作空间和检查点，不要求转换两家的私有聊天文件。

身份、所属空间、实例分支、资料和相关 Work 归属不变。旧端负责准备并交出，新会话由工作台/运行器经 Adapter 创建，不能要求停工后的旧模型继续控制后半段。

交出失败不接手；交出成功而新会话失败则保留交接材料，从接手步骤继续，不重做交出、不静默重新激活旧会话、不改成后台 CLI。它只是用户可见组合，不加第八个 Skill，不因普通断连自动触发。

### 8.4 手动接手是保底路径

用户可在 Codex 当前会话调用 handoff，确认交出后，进入同一个实例目录启动 Claude Code CLI 的新会话，再手动调用 relay。换的是 Harness 和原生会话，不是 Agent 身份。relay 在用户已经打开的新会话中接手，不能再偷偷启动另一个会话；真实会话绑定与停工确认能力按各入口验证，不编造会话 ID 或复用已交出的旧 ID。

文件资料、Skill 和 CLI/MCP 操作是手动路径的基础，但不能假设所有 Harness 自动读取相同的规则与 Skill 目录。接入时验证或提供最小材料加载入口。手动路径通过不代表自动创建、持续通信和自动交接已完成；自动路径不可用时明确报告缺项，不能据此缩减 V1 目标。

## 9. Git 存储、同步与本地副本

main 保存共享配置、关系、管家角色登记、实际采用的 Definition/Skill、执行资格、交接资格和使用中的 Work/Delivery；Git Message Backend 保存正式消息及 ACK。新空间按第 2.3 节放置三份实际内置定义，不为用户未使用的 Work/Definition 生成空占位。

instance/* 保存完整的实例资产、采用版本和历史，不仅是 Instance Context。示例分支名仍可在实现时确认，未执行真实迁移。原生会话只新增记录段，不每会话建分支，不每消息/工单建分支。实例分支不整体合回 main；资产提升只提交明确选定的共享材料。

同机或跨机允许多份副本，可独立 clone 或按条件用 worktree，共享缓存仅是优化，不强制一个本地根。副本存在不是身份、Fork、membership 或执行权。不同实例的可变原生状态不能因底层共仓无意混用；需在真实 Adapter 中验证归属，不能凭目录不同就宣称隔离。

每个 Workspace 指定本地或远端的共享确认位置。副本不必实时全等，但负责人、交付封存和入口变更以共享确认结果为准。工具随操作同步，仅处理本操作文件和分支，不夹带用户别的改动、不自动提交产品。单独同步入口可用于诊断或补齐。

原始记录可持续本地保存并分批同步，不每输出片段远端提交。交出前先保证必要材料可访问。独立消息竞争可重读后补齐；同工单或控制权前提变化则返回冲突，不覆盖或无限重试。

明确区分本地保存、共享确认、部分成功和结果未知。超时先按原操作标识追认，不生成新消息或重做模型/产品业务。成果先保存再登记 Delivery；跨产品/应用仓不是原子事务，消息双写也不扩成所有模块合同。具体频率、缓存、重试预算随实用确定，不预建分布式租约、自动选主和同步平台。

## 10. 公共程序、真实接入与自动看护

### 10.1 轻量公共实现

CLI、模型工具入口和可选 UI 调同一实现。模块操作、存储访问、Message Backend、运行器、Runtime Adapter 与 Channel Bridge 是软件内职责，不是一组必需微服务。普通查询/发布不要求完整 Host 或 UI 常驻，自动运行按需启用。

Harness 自己做推理、工具循环和会话内压缩，平台不再套一个 Agent Loop。已有 App 会话走其控制入口，托管模式由运行器调用原生环境。AgentWorkspace 管理持久实例并替用户操作现成 Harness，不是只管理文件，也不重新制造 Harness。同实例模型执行有序，收件、通知、发送独立推进，长轮次不能堵住模型已明确发出的求助。

必要事实先保存，本地应共同完成的记录使用现有事务能力。配置和存储对象避免无意义重复解析与多层转发。SQLite 可供高频本机记录使用，但不是强制协议，也不能成为未说明的唯一资产容器。不同实例可以共用程序和进程，不共用未区分归属的可变状态。

### 10.2 Desktop 与 CLI 均为正式目标

首批目标为 **Codex（Desktop 与 CLI）、Claude Code（Desktop 与 CLI）、WorkBuddy（Desktop 与 CLI）**。具体桌面产品、CLI 名称与对应关系按实际入口核对；同一品牌的不同入口分别实现、分别验收，不因一侧可用而声称两侧支持。此处列的是要求，不是兼容性认证。

V1 要在 AgentWorkspace 中替用户选择入口与模型配置，为指定实例创建真实会话，加载必要材料，持续投递输入、接收事件和状态，并完成自动交接。仅启动进程、打开窗口、填入 composer 或拿到请求成功结果，不等于真实会话已绑定、材料已加载或 Agent 已就绪。

用户选择 Desktop 就应进入并通信于真实桌面会话，不能用后台 CLI 冒充；桌面持有会话时不另起 writer 抢占。自动新建会话与连接用户明确选择的已有会话分开，扫描发现不代表获得控制权。连接失败不静默 exec resume、不删 writer lock、不改身份或会话冒充恢复。

发现、创建/连接、normal/insert、状态与事件、停工确认、记录取得、定位会话和无人值守运行按真实版本验证并声明能力。缺失、不支持和未验证要可见，不能伪造成功或静默切换 Harness。历史一次成功不等于当前版本稳定承诺。

### 10.3 可选渠道

**企业微信是 V1 要交付的渠道接入目标**，采用可选安装、显式配置与启用的 Channel 插件；未启用企业微信不阻止 Workspace 使用。它处理外部身份、目标映射、输入和明确回复，不是 Harness 或模型服务，不自动公开内部讨论，也不代 Agent 生成 ACK。具体消息类型按已实现、已验收的范围展示，不承诺未验证的多模态能力。

Message Backend 管消息保存和到达，Harness 接入管与真实执行会话通信，Channel Bridge 管外部渠道交互。三者是职责边界，不强制三级转发服务。第三方可按同一接入约定扩展，不先建设插件市场；云端远程入口不成为第四个真值仓。

### 10.4 首版必须看护已启用的连接与桥接

运行器对用户已启用的桥接/收发组件做轻量生命状态监控。恢复需同时确认“用户仍要求运行”和“组件仍服务于当前有效入口”，不能只见进程消失就拉起。

| 情况 | 行为 |
| --- | --- |
| 意外网络断开 | 尝试重连原有效入口。 |
| 受管桥接进程异常退出 | 重新启动对应组件，不启动第二个模型执行者。 |
| 用户关闭、watch stop、handoff 进行中或已交出 | 不自动拉起旧入口的收发或执行。 |
| 鉴权/配置错误或连续恢复失败 | 暂停尝试，明确原因与所需处理。 |

handoff 开始就暂停相关自动拉起，不能等控制权释放才停止看护重启；但不阻断交接材料的正常保存。仅停止 watch 不释放实例控制权，也不自动关闭无关组件。

重连/重启只恢复连接和受管组件，不重跑原模型轮次、不补造 ACK、不重发可能成功的业务、不偷偷创建新原生会话，不自动重启整个 Desktop 抢会话。每次恢复重新核对绑定；归属已变更时旧端不能恢复收件。

采用递增等待与有限尝试，参数依实践确定，不做无限重启风暴或通用调度平台。原执行者真正丢失且没有交接点时仍按唯一执行合同阻塞；连接看护不是自动接管的后门。

### 10.5 Harness 与模型服务是两个独立配置维度

| 维度 | 选择内容 |
| --- | --- |
| Harness / 运行环境 | 产品、Desktop 或 CLI 等入口、所在环境，以及该入口实际支持的操作。 |
| Model Provider / 模型服务 | 该 Harness 使用的服务地址、协议、认证引用及连接设置；实例再选择模型和推理强度。 |
| Channel / 通信渠道 | 企业微信等外部用户沟通入口，与前两者独立。 |

界面不再把三者笼统叫 Provider。Harness 与模型服务是组合关系，不为每个“Harness × 模型服务”组合新增子类或插件。切换底层模型服务不会创建另一个 Agent，也不会让 Message 改为按模型品牌路由。

通用创建入口扫描已支持的程序、标准配置位置及用户登记的连接，允许手动添加；不遍历整个磁盘、抓取其他会话内容或外传凭据。区分已发现、待登录、连接失败、能力未确认与可运行，不把配置文件存在当作认证或模型调用成功。三名管家和用户实例共用该流程。

模型和推理强度优先从当前所选 Harness/服务的真实接口取得。不支持查询时允许明确配置并标注验证状态，不能硬编码“低/中/高”冒充发现结果，不能把一个账号的模型目录用于另一个自有服务。所选模型、服务与强度按实际兼容组合验证；“OpenAI 兼容”或只改 base URL 不构成全部协议与工具能力兼容的证明。

**用户应能让 Codex 或 Claude Code Harness 使用自己的模型服务；尤其支持在兼容前提下，指定 URL 与 API 凭据、仍使用 Codex 的 Harness。** 优先复用原生配置、进程环境和会话参数。每实例保存选择并使用本机凭据引用，不修改其他实例或用户的全局设置；某入口只允许全局配置时必须公开限制，不假装具有实例隔离。

默认配置仅服务预填，模型服务、模型和强度可分别调整；不擅自改用更贵模型、备用端点或不同数据发送目的地。保存配置不冒充当前会话已生效，实际生效配置另行确认；需要新会话才能生效时走交接，不偷偷重启。纯手动会话可沿用用户已在 Harness 配好的服务，但自动配置能力不能因此省略。

#### 10.5.1 实例模型配置由 AW 执行（2026-10-09 确认）

角色和实例可以保存结构化的模型与推理强度选择，由 AW 在调用原生会话接口前读取、校验并显式传入；不能只写在 `AGENTS.md` 或 `startup.md` 中等模型启动后自行遵守，也不能因为调用者省略参数而继承调用者的模型与强度。首次实现限定为 Codex，优先覆盖当前 Codex Desktop 创建、换新会话和后续输入路径，不同时扩展其他 Harness 或建立模型网关。

配置各有一个维护位置：

- 共享 Definition 可选地提供 `definitions/<role>/runtime.json`，仅作为实例创建材料。产品内置通用角色不硬编码具体模型或强度；某个 Workspace 可以为采用的角色选择自己的值。
- 创建时将所选模板复制为实例根的 `runtime.json`；实例此后独立维护，随实例资产与检查点保存。没有 Definition 也可直接配置实例；修改共享模板不覆盖已有实例或运行中的会话。
- `.aw-local/runtime.json` 保留当前环境的原生连接、项目关联、程序位置及必要凭据引用。不得让本机文件和实例文件成为两份互相覆盖的模型选择来源。现有配置迁移须保留原选择和可追溯来源，不以空值、调用者设置或推测值填补。

实例配置按已支持的 Harness/入口组织；模型服务仍为独立选择。当前先实现 Codex 配置段，具体结构随实现确定并公开文档化。账户连接和服务配置变化后，按当前实际入口及服务重新确认适用情况；不能用另一个账号、CLI 或自有服务的模型目录证明当前 Desktop 支持。无法查询时允许用户明确填写并标明未验证，不伪造能力验证。

创建身份仍不要求运行配置，但自动启动必须有明确且结构有效的模型与推理强度；缺失时在创建原生会话或发送模型输入前停止并指出缺项。原生接口支持的明确 `none` 等值不等于缺失。已知不支持的组合不得静默换模型、改强度或切换服务。

创建、换新会话以及后续投递共用同一配置解析规则，并显式传入实例已经选定的模型与强度。运行中的会话继续使用已生效选择；保存新配置或更新模板不等于立即切换，变更应通过明确的应用操作或必要的交接生效。复用原有运行记录说明采用值、配置来源和验证状态；请求参数、原生接受与实际生效须分别记录，不能仅因参数保存或请求成功就声称真实模型设置已核实。

此保证覆盖经过 AW 的会话操作。绕过 AW 的直接原生调用不在保证范围；使用方应通过 AW 的统一入口启动和派发实例。平台不把发现配置、保存配置或缺项检查变成额外的启动授权，也不自动恢复用户已停止的会话。

### 10.6 薄接入、现成能力与插件扩展

实现可以采用一个薄的公共接口或基类，由具体 Harness/入口实现调用原生接口、SDK 或合适的现成模块。只抽取真实共性，保留能力差异，不强制多层继承或只转发的 Service/Manager。核心负责实例、Binding、Message/ACK、检查点和权限校验，接入实现负责外部系统差异，不各自再造一套控制权或恢复协议。

开放最小插件接口、能力说明、示例和契约测试，让后续或第三方逐步补充 Harness 与 Channel；内置与外部接入遵守同一合同。普通自定义模型端点优先通过配置添加，不为每个 URL 编写模型插件。插件由用户明确安装启用，不扫描到就执行第三方代码；不提前建设市场、热更新或通用插件平台。

复用以降低**整体**复杂度为准：优先调用原生能力，不重新实现 Harness 的推理、工具执行或上下文管理。ACP、CC Switch、AgentAPI、LiteLLM 等仅是曾讨论的候选，**未选定为依赖，也不以接入它们为 V1 前提**；具体版本、维护情况、许可与兼容性在采用时重新验证。本文件不记录未经复核的外部支持承诺。

模型协议匹配时 Harness 直接访问用户服务，不强制经过 AgentWorkspace 或代理。确实需要转换时才评估现成网关，并验证事件、工具和推理语义；不自己建设通用网关。“直接 API、没有 Harness”不等于完整 Agent 运行环境，核心不为此自研执行循环；其他 Harness 可经插件后续扩展。

### 10.7 Workspace 级巡检、修复与授权

管家小组处理 Workspace 全部管理事务，监控修复是其中的下属工作，不将 Steward 降格为故障路由器。Workspace 管理授权由用户本次请求或既有明确授权提供，并由程序核对角色对应实例、当前 Binding、目标与动作范围；不凭实例名称、Definition 或提示词取得管理员权限。不要求用户对已授权的普通操作重复确认，也不借管家名义扩大授权。

Sentinel 管理巡检计划，确定性程序负责计时、收集事实和执行基础检查；任务持久保存，能查看执行环境、启停、最近触发与失败原因。计时不能依赖模型一直运行，也不能全部寄生在被监测的那个 Runner 内。多个环境连接同一 Workspace 时不得各自启动重复的小组执行者或重复修复；复用已有单入口与锁，不另建选主平台。

巡检覆盖当前入口与 Runner、消息/ACK 积压、检查点与发布操作、交接等待、Git 可达性、已启用渠道，以及巡检任务自身。报告区分正常、异常、未知和缺少观测；远端机器不可观察时不能声称全局健康。用户暂停、手动入口等待和正常长轮次不能只因超时被判为可接管故障。

基础检查应提供可供 CLI、UI 和模型共同读取的结构化事实，可采用 `workspace doctor` 一类入口，最终命令在实现时确定。正常检查不必调用模型；异常按原标识归并，有限重试、退避，防止重复告警和维修风暴。复杂问题交 Maintainer 诊断，修复后重新检查，保存动作、依据、结果和未决项；无法处理或管家自身失联时，通过仍可用的状态页/已授权通知路径报告，不递归增加“管家的管家”。

自动修复仅限已授权且可验证安全的动作，例如恢复仍启用且属于当前入口的连接或桥接、核对并补齐原操作、无本地冲突的同步。执行前复核前提；用户停用、handoff 中或执行权变化时不能重新拉起。未知发送或模型轮次不得重放，不伪造 ACK、不删除 Binding、不强制接管、不擅自修改产品或清理未决记录。涉及资料覆盖、共享发布、长期职责和权限变化须有对应明确授权；软件升级也不成为自动修改业务资料的理由。

工具侧授权与运行环境权限共同约束维护动作，不能把提示词声明当物理隔离。管家小组不得绕过第 8 节的执行资格与第 10.4 节的恢复边界。

## 11. 工作台的最小产品行为

V1 展示管家小组与用户实例、通用 Harness/模型选择、自动创建会话与换会话入口，以及可确认的会话、收件、巡检、维护、保存/同步状态和材料版本差异。不用一个“在线”混合连接、执行资格、忙闲和 ACK；不能把“身份已创建”显示为“已运行”或“监控已启用”。

自动创建真实会话、持续通信和自动交接是 V1 目标；打开 App、定位指定会话按实际入口能力提供。没有接口时显示缺项与手动保底，不冒充自动支持、不做通用 UI 自动点击，也不把恢复执行 CLI 当成无副作用的“打开会话”。打开仍有效的会话只是导航，不触发 relay 或产生新 writer。

V1 不另造统一聊天客户端，七个 Skill 不必成为七个一级菜单。管家请求可通过已接入的原生会话或授权渠道提出，工作台提供管理入口，不要求先建设自己的聊天界面。自然语言创建与换新会话复用通用操作；无任务开机规则与已授权巡检按第 4.3 节区分。统一工作台聊天留待 V3。

消息显示“已确认通知”，不宣传为已读或处理完成。异常明确失败位置与已确认结果：创建后初始化失败继续完善；交出后新会话失败继续接手；消息发布未知追认/补齐原操作；普通断线重连原入口。不能所有情况都从头“再试一次”。

职责与 Skill 仅比较实际使用的来源文件，不自动评价成长、写长期规则、整理经验或推广共享资产；用户自行掌控。独立分支不是私密/安全隔离承诺，保存与共享范围需如实说明；V1 不假装已有复杂权限系统。

## 12. 七个 Skill 与发布更新

| Skill | 职责 |
| --- | --- |
| workspace | 创建含管家小组的空间、接入、查看、产品关联与好友管理。 |
| work | 可选工单 create/list/show/update/deliver，不规定工作方法。 |
| message | send/list/show/receive/poll/watch 与 ACK；优先使用 AW 工具，也指导仅有仓库工具或 Git 时按相同协议操作。 |
| agent | 通用实例管理、Harness/模型配置与会话创建、可选定义、初始化及显式资产提升。 |
| handoff | 当前入口准备材料并调用 stop 交出。 |
| relay | 首次进入或接手，调用 start 并读取必要材料。 |
| fork | 从检查点创建新实例，进入时复用 relay。 |

保留七个面向用户的 Skill，不因三名管家增加三个同名公共 Skill，也不把 tick/start/stop/resume 拆成新 Skill。三份管家 Definition 与所需配套材料单独维护，复用实际可用工具；检查点与资料说明共用。提供 work Skill 不强迫使用 Work。当前打包 Skill 仍反映 `0.1.0a1` 已实现命令；新增行为随代码实现同步更新，不能先把未实现命令当教程发布。

软件 Release 版本、采用的材料 revision、数据格式版本和对象版本分开。兼容软件升级只更新受管程序，不重置用户职责、分配工单、切换入口或触发交接。确需格式迁移时显式执行，不以开发仓覆盖应用仓；无共享来源仍能正常升级公共工具。不提前建复杂安装、兼容或资产发布平台。

## 13. 首版边界与验收

2026-10-04 补充：设计目标不等于每个版本都支持所有入口和操作。对明确不支持的能力，允许作为本版公开限制交付，不为补齐功能表强行增加复杂或脆弱的适配。必须写明具体入口、缺失操作、用户影响和可选路径，并让用户界面、Agent 进入材料与相关 Skill 可知；不能只藏在开发检查点。当前清单在随包维护的[支持范围说明](../src/agent_workspace/resources/prompts/capabilities.md)。

本版未接入不等于上游永久没有接口；未核实、未登录和真实环境未验收应分别说明。不支持的动作明确停止或保留队头并报告，不暗中切换 Harness、模型或投递语义，也不把明确限制当作自动维修故障。已支持的自动创建、通信与交接仍须完整验证，不以此条替代实现或扩大权限。

现有 `0.1.0a1` 代码、七个 Skill、工作台与原验证记录不因本次设计落档升级为完整 V1。当前安装与命令按 usage.md，新增差距与实现顺序按 [implementation.md](implementation.md)。历史验证保留原事实，不用文档更新补造兼容性或验收结果。

| V1 验收项 | 必须取得的实际证据 |
| --- | --- |
| 管家创建 | 新 Workspace 自动建立三份定义和三个真实实例；重复初始化与部分失败不重复创建、不覆盖同名用户资产；无可用入口时明确待配置。 |
| 通用配置 | 管家和用户实例共用发现与选择流程；Harness/入口、模型服务、模型、强度清楚分开；实际会话采用指定配置，不污染其他实例或全局设置。 |
| 自有服务 | 记录用户已反馈的 Codex CLI 自定义 URL/API 路径并独立实测；验证 Codex/Claude Code 与目标服务的实际兼容组合，不能仅凭配置成功验收。 |
| 六类运行入口 | Codex、Claude Code、WorkBuddy 各自 Desktop/CLI 分列环境和版本；对声明支持的操作验证真实创建、绑定、材料加载、状态/事件和通信，对当前不支持或待确认的操作验证限制提示与禁止静默降级；CLI 不代替 Desktop。 |
| Message 与 Channel | 消息到达目标实例当前原生会话，真实 receive/ACK 生效，旧入口被拒绝；长轮次不阻断发送；企业微信按已授权目标收发，不以启动新会话冒充持续通信。 |
| 自动交接 | 同 Harness 与跨 Harness 均跑通；至少覆盖 Codex 到 Claude Code CLI 的同实例接手，后续消息进入新会话；新端失败不复活旧端或重做业务。 |
| 手动保底 | 旧会话手动 handoff，用户在同一实例目录打开新 Harness 会话并 relay；不另开隐藏会话，不冒充自动化验收。 |
| 管家维护 | 授权计划真实触发、基础检查可独立运行、有限安全恢复与复查留证；小组自身故障可见；暂停/交出/未知结果不被误修、多环境不重复维修。 |

同时保留无用户 Definition/Work 创建、直接创建而不启动、已有定义、无 Work Fork、选定资产提升、独立 Work/Delivery 的回归；不因管家必备定义改变用户实例的可选性。重点验证唯一入口、原操作补齐、不明副作用不重放、资料不丢失与配置隔离。

管家工具所需的最小授权校验属于 V1，复杂权限平台与通用智能安全审查后置。V2 独立身份、V3 统一聊天与多事务、强制接管、Merge、通用流程引擎和完整外部资产迁移仍不纳入本次范围。巡检定时触发和自动会话操作不得再笼统归入“未来复杂自动化”而推迟。

具体基类、插件注册形式、SDK 选用和调度实现由开发者负责，以短调用链、少状态、少重复 I/O、明确错误与真实验收为准。只为实际差异增加代码，不为了采用外部产品改造核心模型。所有技术测试使用隔离数据和明确测试任务，不给用户业务实例安排隐含试做任务。

## 14. 后续方向与来源

### 14.1 V2：Independent Agent

V1 的 A 模型按 Workspace 管身份；V2 的 B 模型使 Agent 身份和工作空间独立，通过参与关系加入多个 Workspace。这是不同产品模型，不是加一个字段或天然更优。多产品、多仓通信、多份本地目录、无 Definition 创建都不等于 V2。

候选物理形态是每 Agent 一个 Repo、每 Workspace 一个 Repo，配合多仓管理；Git 可以保留，不是唯一必须后端。新增责任是独立身份、参与关系、统一执行资格、引用与更新，不只是批量 clone，也不能由每个 Workspace 各自确认同一实例唯一执行。

Definition、权限、消息地址和 Work owner 如何引用独立身份以后统一设计。V1 不预埋半套 membership、继承图、联邦服务或微服务群。Work 到 V2 仍可选，Message Backend 更换不依赖升级身份模型。

实例分支历史可成为迁移来源，但拆 Repo 不是完成身份迁移；还须明确旧消息地址、Work/Delivery 引用、采用版本、入口和参与关系。未来显式迁移，保留来源，不改写封存历史，不随软件升级自动迁移，不承诺无成本无缝切换。

### 14.2 V3：统一工作台与同一身份的多事务会话

将会话界面集中到工作台是后续候选方向，同时保留“一个持久 Agent 身份，用不同事务会话处理不同事情”的工作方式。统一聊天与多事务不是 V1/V2 的依赖，也不是当前实现能力。V1 使用用户选择的原生 Desktop、CLI 等界面，但已经要求支持自动创建、持续通信与交接；不能把这些运行能力推迟到 V3。ACP 或更完整会话界面方案届时按真实收益评估，不在本次落档中指定为基础依赖。

```text
Agent A：共同身份、职责、Skill 与持久资产
    ├─ 事务会话 1：调查构建故障。
    ├─ 事务会话 2：回答使用问题。
    └─ 事务会话 3：按用户要求完善文档。
```

各事务有自己的对话与进展，可以并行；同一事务可以经历多个 Runtime Session，因此事务会话不等同于原生 Session。长期资产属于同一实例，允许共同访问不等于全部实时加载，也不授权平台自动筛选、整理或改写用户记忆。

未来若采用此模式，唯一执行约束下沉到每条事务：每条事务同时最多一个有效入口，共享文件修改仍需版本检查，外部操作不能因多会话重复执行。Work 仍可选；有 Work 时明确实际执行关联，不把会话当成新 Agent 身份。V1 继续实行整个实例唯一入口，不提前放开。

新建事务会话用于同一 Agent 开始另一件事；handoff/relay 用于同一事务换入口接续；fork 才创建独立 Agent。单条事务交出不停止其他事务；整个实例归档须处理所有有效入口。这些细节在 V3 统一设计，不在 V1 增加半套对象。

消息需要沿明确关联路由，不能广播给全部会话或一律发给最近活跃会话；无关联消息的接入规则留待 V3 明确。V2 解决参与哪些 Workspace，V3 解决同时怎样处理事务与交互，二者是不同维度，不互为技术前提。
